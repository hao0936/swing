# Reflection Report (English)

The implementation follows the Part 1 design by translating the three-tier architecture into clear Java packages. The data tier is represented by `DataStore` plus CSV read/write helpers. It loads the provided datasets into in-memory collections and persists changes back to CSV, which matches the “no database” constraint while preserving the idea of a shared clinical record store. The business logic tier is implemented with services such as `AppointmentService`, `PrescriptionService`, `EHRService`, and `ReferralCoordinator`. These services encapsulate rules like appointment conflict checking, prescription creation, and referral lifecycle updates. The presentation tier is the Swing GUI: each role’s access is represented through panels and tables, with actions to add, edit, delete, and export records. This mirrors the role-based interfaces described in the design narrative (patient, clinician, and admin functions) without adding unnecessary complexity.

The class model from Part 1 is reflected by concrete domain objects: `Patient`, `Clinician` with subclasses (`GeneralPractitioner`, `SpecialistDoctor`, `Nurse`), `Appointment`, `Prescription`, `Referral`, `Facility`, and `Staff`. Relationships are explicit: patients hold a `HealthRecord`, which is updated by prescriptions and referrals, and IDs link clinicians, facilities, and appointments. The referral flow is centralized in the singleton `ReferralCoordinator`, exactly as required. The singleton ensures one shared referral queue, consistent status updates, and a single audit trail, which prevents duplication and keeps the referral process synchronized across the system. Email is simulated by text export, fulfilling the requirement to generate a referral message without sending real messages.

MVC is used to structure the codebase. Models are the domain classes (data-only objects), views are Swing panels and table models, and the controller layer is the `AppController` that mediates between user actions and services. Each panel updates its own table model while delegating business actions to the controller, which keeps UI logic separate from data manipulation. This separation makes it easier to change the UI language or export logic without touching the business rules. It also supports future enhancements: adding validation or access control can be done in services and controllers without rewriting the UI.

The language toggle demonstrates a simple UI-level concern implemented cleanly through MVC. The views request translated text from the `I18n` utility and refresh labels on language change, while models and controllers remain language-agnostic. This matches the design goal of keeping presentation concerns in the presentation tier.

Overall, the implementation demonstrates how the Part 1 design informs concrete classes, interactions, and responsibilities. The layered structure, MVC, and singleton pattern are not just theoretical; they drive the runtime behavior of scheduling, prescriptions, and referrals. The main limitation is that data validation and role-based permissions are minimal due to scope and time. If extended, I would add stronger validation, role-based access checks, and more detailed audit logging, while keeping the same MVC and service-based structure.
